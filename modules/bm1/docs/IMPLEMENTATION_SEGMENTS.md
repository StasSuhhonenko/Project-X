### C2 persistent-state design gate

The revisit, identity and save requirements above already apply. Before the
first mutable C2 child changes runtime code, record and review its concrete
ownership/transition design in that child's documentation. Current travel
reconstructs static destinations and allocates fresh spatial runtime IDs;
current restore validates authored station composition. Neither behavior defines
the future persistent-world contract. Resolve only the consumed slice:

- Identify immutable module defaults, persistent mutable system facts, active
  simulation entities and renderer projections separately. Name the sole
  authority for each mutable fact while active/inactive and any validated
  handoff; do not create independently writable scene and system copies. Use
  evidence to distinguish persistent entities, respawns and scene-local state.
- Distinguish content, persistent identity and runtime instance references.
  Specify reactivation/restore identity or mapping, allocator ownership and
  reference cleanup so revisits cannot duplicate persistent entities or reset
  their accepted mutations; document source-required lifetime exceptions.
- Define departure/arrival's atomic scope across origin and destination changes,
  fuel/date, IDs and consumed RNG state. Preflight must not mutate those facts.
  Extend exact-arrival rollback to all affected persistent state; preserve
  pending-arrival mutation/save locks and reject stale callbacks after session
  replacement. Failure/retry must not leave hidden cache changes or repeat work.
- Specify saved authoritative facts and reconstruction/validation of the active
  system, including the fixed-composition checks that must change. Apply the
  existing migration-or-explicit-rejection policy. Demonstrate mutation, leave,
  revisit and reload from both sides, plus refused departure, preload/readiness
  failure, retry and invalid restore without resets, duplicate effects or
  mutation of the live world/stored record on failure.

This is a pre-implementation decision within C2, not a new segment dependency,
chosen storage layout or authorization for background simulation. Inactive-system
time, remote fleets, construction and production retain their C11-C14 owners and
evidence requirements.

### Combat extension decisions

Before C4 or C10 extends the current immediate player-shot path, document the
consumed behavior's deterministic order and lifecycle in its owning child task.
Existing fixed-step/RNG/atomicity rules already apply; the present tick-order
tests do not decide reciprocal combat or projectile semantics.

Decide which snapshots player/NPC decisions read and the order of movement,
firing, projectile creation/advancement/impact, cooldowns, repair, destruction and
terminal settlement. Resolve same-tick lethal exchanges, absent targets and
shots whose emitter is removed. Specify stable processing order, RNG ownership
and draw order, authoritative in-flight state versus visual effects, once-only
hit/effect consumption, and save/restore/departure/rollback behavior. Cover the
chosen rules with deterministic continuation and failure scenarios; preserve
unaffected accepted immediate-hit behavior. C4 owns weapon behavior and C10 owns
NPC decisions; neither requires implementing the other's entire family first.
Choose only evidence-required contracts, not a speculative combat framework.
Apply the [shared notification requirement](../../../docs/ARCHITECTURE.md#components-and-ownership)
when extending outcomes; preserve BM1 wording/notice behavior during any later
correction of the current shared destruction-message exception.
